# SQL DDL Audit – Findings & TODO

Items discovered during Q&A review of `plugins/rigorous-dev/mcp-server/schema.sql`.

| # | Table / Line | Finding | Proposed Fix | Status |
|---|-------------|---------|-------------|--------|
| 1 | `revision` (DDL comment) | Comment `-- Revisions: producer-critic loops within a phase` is ambiguous — reads as if one revision could span multiple loops. | Reword to: `-- Each row = one producer-critic loop attempt within a phase` | Pending |
| 2 | `persona` (scoping & dedup) | Personas are conceptually project-scoped (they represent the app's users), but the schema ties them to a `revision_id` (iteration-scoped). **Three issues:** (a) No `UNIQUE` constraint on `name` — nothing prevents duplicate personas across iterations with different IDs. (b) `ON DELETE CASCADE` on `revision_id` means a persona is destroyed if its last-touching revision is deleted, even if other iterations reference it. (c) Persona lifecycle should not be coupled to revision or iteration mutations. | Re-scope persona to project-level: replace `revision_id` with `project_id` FK, add an `introduced_in_iteration_id` column (tracks when the persona was first created, informational only — no cascade), add `UNIQUE(project_id, name)` to prevent duplicates. Persona rows must not be cascade-deleted by revision or iteration deletions. The existing `requirement_persona` and `persona_addressed` junction tables remain unchanged (they reference `persona(id)` directly). | Pending |
| 3 | All `revision_id` tables → `iteration_id` | 25 tables use `revision_id` as a provenance FK, but in practice only iteration-level scoping matters. The `revision_id` forces an unnecessary `revision → phase → iteration` join chain and couples entity lifetimes to revision deletions via `ON DELETE CASCADE`. **Tables to migrate** (replace `revision_id` with `iteration_id INTEGER NOT NULL REFERENCES iteration(id) ON DELETE CASCADE`): `requirement`, `requirement_trace`, `adr`, `component`, `technology_choice`, `architecture_overview`, `data_entity`, `config`, `approved_dependency`, `user_flow`, `screen`, `info_architecture`, `persona_addressed`, `ux_asset`, `plan_phase`, `plan_overview`, `plan_metadata`, `implementation_manifest`, `intermediate_asset`, `test_report`, `security_audit_finding`, `performance_audit_finding`, `documentation_manifest`, `deployment_manifest`, `entity_snapshot`. **Exception:** `vcs_commit` already has `iteration_id` but MUST have a `revision_id` column **added** (commits are tied to a specific producer-critic attempt). `vcs_commit` is **append-only** — rows must never be updated; each revision produces a new record with its own commit. **Ripple effects:** (a) `entity_context` VIEW becomes unnecessary — drop it. (b) All `idx_*_revision_id` indexes become `idx_*_iteration_id`. (c) `entity_snapshot` UNIQUE constraint changes from `(entity_type, source_id, revision_id)` to `(entity_type, source_id, iteration_id)`. (d) UNIQUE constraints on other tables that include `revision_id` (e.g. `config`, `approved_dependency`, `plan_overview`) must be updated to use `iteration_id`. (e) `persona` is excluded — already handled by finding #2 (project-scoped). | Pending |
| 4 | `system_io` → `data_exchange` | Table name `system_io` is overloaded and easily confused with OS or network I/O. The table actually describes external data flows crossing the application boundary (e.g. "Customer order feed from ERP", "Monthly billing report to S3"), with columns for `direction` (input/output), `source`, `destination`, and `data_format`. | Rename table from `system_io` to `data_exchange`. Update all references: DDL, indexes, `entity_type` values in MCP tool handlers (`write-tools.js`, `read-tools.js`), agent prompts, table documentation (`requirements.md`), and `schemas-overview.md`. | Pending |
| 5 | `adr` / `adr_alternative` (no selected tracking) | There is no way to know which `adr_alternative` was actually chosen for an ADR. The `adr` table has `decision` and `rationale` TEXT columns that describe the choice in prose, but no structural link to the selected alternative row. | **Three changes:** (a) Create a new `adr_decision` table: `adr_id TEXT NOT NULL REFERENCES adr(id) ON DELETE CASCADE, alternative_id INTEGER NOT NULL REFERENCES adr_alternative(id) ON DELETE CASCADE, rationale TEXT, decided_at TEXT NOT NULL DEFAULT (datetime('now')), PRIMARY KEY (adr_id)`. PK on `adr_id` enforces exactly one decision per ADR; absence of a row means no decision yet. (b) Remove `decision TEXT NOT NULL` and `rationale TEXT NOT NULL` columns from the `adr` table — they become redundant (replaced by `adr_decision.rationale` + the linked `adr_alternative.option_text`). (c) Update MCP tool handlers, agent prompts, and table documentation to reflect the new structure. | Pending |
| 6 | `technology_choice` (drop table) | `technology_choice` adds no value over ADR + `approved_dependency`. Strategic technology decisions (why React over Vue?) belong in `adr` with alternatives weighed via `adr_alternative`; the selected choice is now captured by `adr_decision` (finding #5). Concrete packages with versions belong in `approved_dependency` (which already has `adr_id` FK for traceability). `technology_choice` duplicates both with less rigor — no alternatives, no supply-chain analysis. | **Drop `technology_choice` entirely.** Remove the table, its index (`idx_technology_choice_name`), and the `idx_technology_choice_revision_id` index. Remove from finding #3's migration list. Update `entity_type` mappings in MCP tool handlers (`write-tools.js`, `read-tools.js`), agent prompts, and table documentation. If the `category` grouping concept (e.g. "backend-language", "database", "ci-cd") is valuable, add a `category` column to `approved_dependency`. | Pending |
| 7 | `architecture_overview` + `architecture_diagram` (drop tables) | The architecture phase produces version-controlled markdown documents committed to the repo. `architecture_overview` stores only a `description TEXT` and `principles JSON` — both of which are sections of that markdown document. `architecture_diagram` is a registry of file paths (`path TEXT`) that `asset_deliverable` already tracks. Storing prose and diagram paths in the DB duplicates what's already in VCS. | **Drop both `architecture_overview` and `architecture_diagram`.** Remove tables, the `idx_architecture_overview_revision_id` index, and all references. Architecture narrative and principles live in the committed markdown doc. Diagram file references are handled by `asset_deliverable`. Update MCP tool handlers, agent prompts, and table documentation. | Pending |
| 8 | `data_entity` + `data_entity_attribute` + `data_entity_relationship` (drop tables) | These three tables model the target system's data model (ERD) in normalized form — entities, their columns, and FK relationships. This is unnecessary complexity in the DB; ERD-level detail is better expressed as a markdown document (with tables, relationship descriptions, and optional Mermaid diagrams) produced during the architecture phase and version-controlled in the repo. | **Drop all three tables** (`data_entity`, `data_entity_attribute`, `data_entity_relationship`) and their indexes. **Critical requirement:** the backend_architect agent MUST still produce a data model document as part of the architecture phase — a committed markdown file covering entities, attributes, relationships, cardinality, and constraints. Update agent prompts to mandate this deliverable. Update MCP tool handlers, entity_type mappings, and table documentation. | Pending |
| 9 | Config/spec tables → architectural documents (drop 3 tables) | Several tables store configuration or design detail data that duplicates content already produced as version-controlled markdown documents during their respective phases. These tables add schema complexity without enabling meaningful relational queries — they are key-value or descriptive stores better expressed in prose. **Tables to drop:** (a) `config` — key-value design settings (auth schemes, scaling policies, color tokens, accessibility); covered by architecture and UX design docs. (b) `screen_state` — named UI states (loading, empty, error) per screen; covered by UX wireframe/spec docs. (c) `screen_responsive_variant` — breakpoint-specific layout changes per screen; covered by UX wireframe/spec docs. **Tables kept:** `nonfunctional_requirement`, `info_architecture`, `component_interface`, `integration_test_boundary`. | **Drop 3 tables** (`config`, `screen_state`, `screen_responsive_variant`) and their indexes. **Critical requirement:** agent prompts MUST mandate these as sections in their respective committed markdown documents. Update MCP tool handlers, entity_type mappings, and table documentation. | Pending |
| 10 | `user_flow_step_branch` → merge into `user_flow_step` | `user_flow_step_branch` is a small child table (only `condition TEXT` and `next_step INTEGER`) that is always read/written as a unit with its parent step. The separate table adds a join for no relational benefit. | **Drop `user_flow_step_branch`.** Add a `branches JSON` column to `user_flow_step` (nullable, e.g. `[{"condition": "valid credentials", "next_step": 3}, {"condition": "invalid", "next_step": 5}]`). NULL for non-decision steps, populated when `is_decision_point = 1`. Update MCP tool handlers, agent prompts, and table documentation. | Pending |
| 11 | `plan_phase*` → `work_item*` (rename 3 tables, drop 5) | `plan_phase` collides with the core `phase` table (the 9 SDLC stages) and is misleading — it's actually a discrete work item within the implementation plan, not a phase. **Tables to rename:** `plan_phase` → `work_item`, `plan_phase_requirement` → `work_item_requirement`, `plan_phase_component` → `work_item_component`, `plan_phase_risk` → `work_item_risk`. **Drop 5 tables:** (a) `plan_phase_api_endpoint` — redundant with `component_interface`; work item → component → interface already implies which endpoints to deliver. (b) `plan_phase_db_change` — DB migrations are implementation details derivable from data model docs + component scope. (c) `plan_phase_flow` — derivable via `work_item_requirement` → `requirement_trace` → flows. (d) `plan_phase_screen` — derivable via `work_item_requirement` → `requirement_trace` → screens. (e) `plan_phase_relationship` — ordering/parallelism between work items is over-engineered as a graph; replace with a nullable `work_order INTEGER` column on `work_item`. Items with the same `work_order` can run in parallel, NULL means unordered. | **Rename 4 tables, drop 5.** Add `work_order INTEGER` column to `work_item`. Update all FK references (e.g. `plan_phase_id` → `work_item_id` in `implementation_manifest`, `plan_overview_risk.plan_phase_number`), indexes, MCP tool handlers, agent prompts, and table documentation. | Pending |
| 12 | `plan_overview_risk` → merge into `plan_overview` | `plan_overview_risk` stores plan-wide risks (risk text, mitigation, optional phase number). This is simple descriptive data with no FK relationships beyond its parent — no reason for a separate table. | **Drop `plan_overview_risk`.** Add a `risks JSON` column to `plan_overview` (e.g. `[{"risk": "...", "mitigation": "...", "work_item_number": 3}]`). Update MCP tool handlers, agent prompts, and table documentation. | Pending |
| 13 | `plan_metadata` (drop table) | `plan_metadata` tracks plan version, status, date, and upstream spec versions (`requirements_version`, `architecture_version`, `ux_specification_version`). All redundant: plan `status` is already on the `phase` table, document versioning is handled by git, and upstream phase completion is tracked by the `phase` rows within the same iteration. | **Drop `plan_metadata`.** Remove table and its index. Update MCP tool handlers, agent prompts, and table documentation. | Pending |
| 14 | `implementation_manifest` + 7 children (drop 8 tables, re-parent 4) | `implementation_manifest` is derivable from `vcs_commit` + git/CI metadata. Its child tables cascade into the same analysis. **Drop 8 tables:** (a) `implementation_manifest` — status, LOC, build result, commit SHA all derivable from VCS/CI. (b) `implementation_file` — file changes are git diffs. (c) `implementation_file_requirement` — file→requirement mapping derivable from `requirement_trace`. (d) `implementation_api_endpoint` — endpoint existence verifiable from code. (e) `implementation_api_endpoint_requirement` — endpoint→requirement lives in `requirement_trace`. (f) `implementation_dependency_added` — package managers (`package.json`, `go.mod`) in git are source of truth. (g) `implementation_db_migration` — migration files tracked in git; status is CI/deployment concern. (h) `implementation_review_checklist` — one-time gate; critic's `revision` verdict captures the outcome. **Keep 4 tables, re-parent to work item or iteration:** (a) `implementation_requirement_status` — agent-assessed "is REQ-042 done?" not derivable from git. (b) `implementation_component_status` — agent-assessed component completion status. (c) `implementation_blocker` — structured impediment tracking with severity/escalation. (d) `implementation_blocker_requirement` — blocker→requirement traceability. | Pending |
| 15 | `vcs_commit` redesign | Current `vcs_commit` has a nullable `phase_id` FK to the SDLC `phase` table. Commits should map 1:1 to a work item, not loosely to a phase. Also per finding #3, `revision_id` must be added. | **Redesign `vcs_commit`:** (a) Replace `phase_id INTEGER REFERENCES phase(id) ON DELETE SET NULL` with `work_item_id INTEGER NOT NULL REFERENCES work_item(id) ON DELETE CASCADE` — every commit belongs to exactly one work item. (b) Add `revision_id INTEGER NOT NULL REFERENCES revision(id) ON DELETE CASCADE` per finding #3 (commits are tied to a specific producer-critic attempt). (c) Table remains **append-only** — rows must never be updated. (d) Keep `iteration_id` and `UNIQUE(iteration_id, commit_sha)`. Update MCP tool handlers, agent prompts, and table documentation. | Pending |
